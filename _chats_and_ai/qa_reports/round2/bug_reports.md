# QA Bug Reports

## Bug 1: Збій завантаження фонових зображень сцени (Background Asset)
**Severity:** Critical
**Симптом:** При завантаженні зображення через "Edit Scene" лоадер зависає або видає помилку мережі.
**Причина:** Клієнтська частина використовує `POST /api/assets/uploads` та `POST /api/assets` для ініціалізації та фіналізації завантаження в GCS. Однак у бекенд-роутері `assets.ts` і `AssetService` ці POST-методи відсутні (реалізовано лише GET-запити). Сервер повертає 404.
**Fix Plan:**
1. Винести типи завантаження у спільний пакет `@vtt/shared`.
2. Додати методи `initImageUpload` та `finalizeImageUpload` у бекенд `AssetService`.
3. Реалізувати відповідні `POST` ендпоінти в `routes/assets.ts` із перевіркою ролей (RBAC).

## Bug 2: Немає завантаження файлу для токенів + Не відображаються зовнішні URL
**Severity:** High
**Симптом:** При створенні токена немає кнопки завантаження файлу (тільки поле для URL). Якщо вставити URL картинки з інтернету, замість неї на полотні відображається кольоровий квадрат.
**Причина:** 
1. UI компоненти (`AddTokenButton.tsx` та `TokenEditModal.tsx`) не мають інтеграції з сервісом завантаження аспектів, приймаючи лише строковий URL.
2. Зображення на Konva-полотні завантажуються через хук `useImage`, який встановлює `img.crossOrigin = 'anonymous'`. Якщо сторонній сервер (звідки взято URL) не віддає правильні CORS-заголовки, браузер блокує завантаження картинки, і спрацьовує `onerror` хука.
**Fix Plan:**
1. Інтегрувати компонент `ImageUpload` / `AssetPicker` у форми створення та редагування токенів (`AddTokenButton` та `TokenEditModal`).
2. Оскільки ми полагодимо завантаження аспектів у першому багу, токени будуть завантажуватись у наш GCS бакет. GCS бакет має власні налаштування CORS, тому зображення з нашого сервера успішно завантажуватимуться на canvas з `crossOrigin = 'anonymous'`.

## Bug 4: Втрата напрацювань (Data Loss) у функціоналі AI Assistant та завантаженнях
**Severity:** Critical
**Симптом:** Будь-який контент, створений через `AssistantPanel` (чат з LLM, згенеровані зображення та музика), або завантажений користувачем вручну (описано в Bug 1), "губиться" при оновленні сторінки або закритті панелі. Для користувача це виглядає як повна втрата напрацювань.
**Причина:** 
1. **Текстовий чат (LLM):** Зберігається виключно в клієнтському Redux стейті (`assistant.ts`). У базі даних немає жодної моделі (`AssistantMessage` тощо) для збереження історії діалогів з AI.
2. **Медіа (Зображення/Музика):** Хоча бекенд *зберігає* їх у `AssetRepository` (метод `storeAiAsset`), клієнтський інтерфейс (`RecentGenerations.tsx` та вкладка History) повністю захардкоджений (моки "—", "Empty"). Згенерований результат існує лише в локальному React-стейті (`imageResult`), і при закритті вкладки лінк зникає.
3. **Завантаження користувача:** Відсутні POST-ендпоінти для збереження метаданих у БД (Bug 1).

**Fix Plan:**
1. **Persistence для AI Chat:** 
   * Створити таблицю в БД (наприклад, модель `AiChatHistory` або розширити `ChatMessage` режимом `assistant`).
   * Реалізувати ендпоінт для завантаження історії діалогів при гідратації кімнати.
2. **Інтеграція RecentGenerations:**
   * Підключити компонент `RecentGenerations.tsx` до ендпоінту `GET /assets?roomId={id}`.
   * Виводити останні згенеровані картинки та аудіотреки, щоб користувач міг повернутися до них, переглянути та використати в сцені.

## Bug 5: Не працює малювання та редагування Fog of War (Туман війни)
**Severity:** Critical
**Симптом:** Майстер (GM) не може малювати або стирати "туман війни" на сцені. Інструмент "Fog" вибирається, з'являється бейдж "Fog edit mode", але клік та перетягування по полотну нічого не роблять. Користувач підозрював проблеми із завантаженням зображення, але маска туману працює як бітмап, а не як картинка.
**Причина:** 
Функціонал взаємодії з canvas для туману **повністю відсутній**:
1. У `useToolHandlers.ts`, де обробляються всі інструменти (draw, ruler, ping, text), немає жодної умови для `activeTool === 'fog'`. Відповідно, події `onMouseDown`, `onMouseMove` та `onMouseUp` ігноруються.
2. В `api/socket.ts` відсутня функція для відправки змін туману на сервер (немає `emitFogUpdate` або чогось подібного), тому клієнт навіть фізично не може повідомити сервер про зміни.
3. Кнопка "Clear fog (reveal all)" в `EditorToolbarLeft.tsx` лише змінює локальний Redux-стейт (`dispatch(clearFogMask())`), але не синхронізує це очищення з бекендом.
**Fix Plan:**
1. **Обробники подій:** Додати логіку для `activeTool === 'fog'` у `useToolHandlers.ts`. Розраховувати координати клітинок сітки на основі кліку миші (`Math.floor(x / gridSize)`).
2. **Алгоритм малювання:** Реалізувати збереження намальованих клітинок у масив під час `onMouseMove`.
3. **Синхронізація (Client -> Server):** Додати в `api/socket.ts` функцію для відправки `FogMaskDiffPayload` на сервер під час `onMouseUp` (по аналогії з free-draw strokes).
4. **Очищення туману:** Оновити логіку кнопки "Clear fog", щоб вона викликала API для скидання туману для поточної сцени, а не лише міняла локальний стейт.

## Частина 2: Аналіз взаємодій на Canvas (Переміщення та Видалення об'єктів)

Я проаналізував логіку роботи `TokenLayer`, `AnnotationLayer` та інструментів в цілому. Порівнюючи з популярними VTT (Foundry, Roll20, Miro), були виявлені як критичні баги, так і серйозні недоробки UX.

### Bug 6: Konva Crash під час взаємодії з токеном (`getParent` undefined)
**Severity:** High
**Симптом:** При кліку або перетягуванні токена додаток падає з помилкою `TypeError: Cannot read properties of undefined (reading 'getParent')`.
**Причина:** 
У файлі `TokenLayer.tsx` умовний елемент `ghost` (прямокутник, що показує місце, куди впаде токен) рендериться без React-властивості `key`. 
```tsx
{ghost && <Rect x={ghost.x} y={ghost.y} ... />}
{tokens.map((token) => <TokenNode key={token.id} />)}
```
Через специфіку React-Konva, коли `ghost` зникає (`setGhost(null)` під час події `onDragEnd` або кліку), React намагається переіндексувати дочірні ноди. Оскільки `ghost` не мав ключа, React-Konva випадково звертається до видаленої або сусідньої ноди (токена) і намагається викликати в неї `getParent()`, що спричиняє краш усього полотна.
**Fix Plan:**
Додати `key="ghost"` до компонента `Rect` у `TokenLayer.tsx`.

### Bug 7: Неможливість видалити намальовані лінії та текст
**Severity:** High
**Симптом:** Майстер може малювати маркером (`draw`) та створювати текст (`text`), але не може їх видалити або відредагувати. Вони залишаються на полотні назавжди.
**Причина:** 
1. **Лінії:** На бекенді та в `socket.ts` імплементовано метод `emitDrawClear(roomId, sceneId)`, але в UI немає жодної кнопки (наприклад, кошика), яка б викликала цю функцію. Окремо стерти лінію "ластиком" неможливо, оскільки такого інструменту немає (хоча інструмент `select` є, він не виділяє лінії).
2. **Текст:** Є API метод `apiDeleteAnnotation`, але немає UI взаємодії для тексту. На текст не можна клікнути (`listening={false}` у `TextLabel`), щоб викликати контекстне меню чи натиснути Delete.
**Fix Plan:**
1. Додати кнопку "Clear Drawings" (Стерти все) у панель інструментів (для GM).
2. Опціонально (Medium effort): додати інструмент "Eraser", який видалятиме `stroke`, якщо координати миші перетинаються з лінією.
3. Зробити тексти інтерактивними (`listening={true}`) з можливістю видалення через клік (як токени).

### Пропозиції щодо покращення (UX & Feature Gap vs Competitors)

У порівнянні з "нормальними" VTT (Roll20, Foundry), існують наступні недоліки переміщення та виділення:

1. **Гарячі клавіші (Delete / Backspace):** Зараз токен можна видалити лише через правий клік -> "Delete" (Context Menu). Необхідно додати глобальний `KeyboardEvent` лісенер: якщо токен виділено (є `selectedTokenId`), натискання `Delete` або `Backspace` має викликати `apiDeleteToken`. Це стандарт індустрії.
2. **Snapping (Прилипання до сітки):** `TokenNode` має жорстко зашитий `snap` до сітки (`Math.round(value / gridSize)`). У стандартних VTT завжди є можливість переміщувати об'єкт **без прив'язки**, якщо під час перетягування затиснута клавіша `Alt` або `Shift`.
3. **Групове виділення (Select Box):** Інструмент `select` зараз існує лише як стан курсору. Неможливо затиснути мишу, намалювати прямокутник виділення і перетягнути декілька токенів одночасно. Це сильно уповільнює налаштування великих сцен.

## Bug 8: Утечка стану активної сцени між кімнатами (Cross-room scene leakage)
**Severity:** Critical
**Симптом:** Якщо зайти в кімнату, де немає активної сцени, на екрані відображатиметься активна сцена з попередньої кімнати. А при зміні активної сцени майстром, інші гравці не бачать змін, поки не оновлять сторінку. Крім того, "Edit scene" завантажує активну сцену замість обраної для редагування.
**Причина:**
1. **Leakage:** При виникненні помилки завантаження сцени (наприклад, 404 No Active Scene) клієнтський Redux-стейт не очищується (`clearScene` не викликається).
2. **Sync:** Сервер не сповіщає клієнтів (через WebSockets) про зміну активної сцени.
3. **Editor:** `SceneEditor` не робив запит за `editingSceneId`, а покладався на вже існуючий у стейті `scene.current`.
**Fix Plan (Виконано):**
1. В `GameRoom.tsx` додано виклик `dispatch(clearScene())` при невдалому гідратуванні `session:resync`.
2. В бекенд (`server/src/index.ts`) додано подію `scene:activated`, що надсилається через socket.io всім у кімнаті.
3. В `GameRoom.tsx` додано прослуховувач `scene:activated`, який перезапускає завантаження активної сцени без рефрешу сторінки.
4. `SceneEditor.tsx` тепер здійснює `apiFetch` конкретної сцени за `editingSceneId` при монтуванні.
